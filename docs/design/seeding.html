Seeding

How a development database gets its sample trust, land, homes, households, purchases and leases, and how a demo trust gets the same data.

Code: src/CommonGround.API/Infrastructure/Seeding and src/CommonGround.SharedKernel/Infrastructure/Seeding. Last checked against the code: 2026-11-13.

1. Running it

  • npm run db:seed seeds and skips what is already seeded. npm run db:reset wipes the database first. The API never seeds at startup, and an empty database gives an empty app.
  • Both run dotnet run --project src/CommonGround.API -- seed (SeedCommand). It starts the API's services without a web server, so it can run while the API is up. It exits with 1 outside Development or when a seeder fails.
  • A fresh seed takes about 12 seconds. SeedCommand sets the Marten daemon to poll every 50 ms, because the seeders wait for it often.
  • An ERR log line with a ConcurrencyException during seeding is a handler's first attempt, which Wolverine retries. It is not a failure.

2. The seeders and their order

SeedRunner runs every IDevelopmentSeeder in the order AddDevelopmentSeeders registers them (DevelopmentSeeder.cs). Between seeders it waits until no events or messages are left to deliver, because each seeder builds on what the earlier ones and their event handlers made.

  1. TrustsSeeder (in TrustManagement)
  2. LandParcelsSeeder, HomesSeeder, DevelopmentProjectsSeeder (in PropertyRegistry)
  3. UsersSeeder
  4. HouseholdsSeeder, with the households' applications
  5. IncomeLimitsSeeder
  6. GroundLeaseTemplatesSeeder
  7. HomeSelectionsSeeder: choosing a household for a home, in one step from the waiting list on the choice's date, starts its purchase.
  8. PurchaseWorkflowsSeeder: progress on those purchases. A closed purchase creates its ground lease and stewardship case.
  9. GroundLeasesSeeder: activity on those leases, and leases created directly.
  10. StewardshipCasesSeeder, ForeclosurePreventionCasesSeeder, ResalesSeeder, ImprovementRequestsSeeder, HeirTransfersSeeder, LeaseFeesSeeder
  11. RemindersSeeder: reminders the seeder sets, dated so some show on Today, some are upcoming, one was done lately and one was done too long ago for the Reminders page to list.

Seeders from UsersSeeder on are in the API project, because they read records from several contexts. Context projects don't reference each other, with one exception: PropertyRegistry references TrustManagement for TrustSeedLookup.

3. Seed files

Each seeder reads one embedded JSON file next to it, such as homes.seed.json:

{
  "seedKey": "home-downtown-civic-001",
  "trustSeedKey": "dev-default",
  "landParcelSeedKey": "lp-downtown-civic-001",
  "registeredDate": "today-4y",
  ...
}
  • Seed keys name entries and link them: this home sits on the parcel with seed key lp-downtown-civic-001. After writing an entry, the seeder stores a …SeedLookup document that maps the seed key to the real ID. Later seeders find IDs through the lookups, and a rerun skips every entry that has one. The lookups are in each context's Infrastructure/Seeding.
  • Dates are a fixed ISO date (2021-09-15) or relative to the day seeding runs: today, today-30d, today+2w, today-6m, today-5y (SeedDate). Relative dates keep the data current. today-1y is the only relative date that is always in the last calendar year, which a yearly report needs.

4. How a seeder writes

  • Through the domain, not the API. A seeder calls the aggregate's methods (Home.Register, Household.Register) and starts the stream itself. The seed data passes the same rules as the endpoints, and other contexts react to its events as they do in the app.
  • On the seed date. SeedClock.RunAsync gives the seeder its own clock, and MoveTo(date) sets it, at 10:00 in the trust's time zone by default. Events carry that date in OccurredAt. Event handlers run at the time of the event they react to, so their records get the seed date too.
  • Waiting for other contexts. When a seeder needs what a handler in another context makes, such as the purchase a home selection starts, it calls PropagationWaiter.WaitForAsync or WaitForIdleAsync first. Their timeouts use real time, not the seed clock.

5. Demo trusts

A SeedRun is one pass of the seeders. db:seed uses SeedRun.Development (key dev). A demo sandbox starts a run with its own key and a SeedRunTrust, which seeds the seed file's one trust under a new ID and name. Only the trust lookups are keyed by run. Every other lookup is a document in its trust's tenant, so a new trust starts with none. Seed clocks are scoped to their call chain, so a demo run can go on while the API serves requests and while another run seeds another trust.

6. Adding seed data

  • More of an existing record: add an entry to its JSON file with a new seed key, then run npm run db:seed.
  • A new kind of record: write an IDevelopmentSeeder and a seed lookup for it, and register the seeder in AddDevelopmentSeeders after the seeders it builds on. Use SeedClock for dates and PropagationWaiter before reading another context's records.
