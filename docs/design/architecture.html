Architecture Overview

How CommonGround is built: the processes, the bounded contexts inside the API, how data and messages move between them, and why it was built this way.

Last checked against the code: 2026-11-13.

1. Purpose and audience

CommonGround is software for community land trusts (CLTs). A CLT owns land and sells the homes on it to income-qualified households under a long ground lease, with a resale formula that keeps the home affordable for the next buyer. Staff use CommonGround to run that work: the waiting list, applications, home sales, ground leases, lease fees, resales and stewardship. The product goal is a free or low-cost alternative to the commercial CLT software.

This document is for a developer who joins or forks the project. It assumes you know C#, ASP.NET Core and React. It doesn't assume you know CLTs, Marten or Wolverine.

Words used throughout:

Trust
One CLT using CommonGround. Each trust is a tenant; its data is separated from every other trust's.
Bounded context
One area of the domain with its own model and its own project, such as HomeBuyers or Homeownership.
Gateway
A backend-for-frontend (BFF) process. It owns sign-in and cookies, and calls the API for the browser.

2. The system at a glance

A staff member's browser talks to one origin, the management gateway. The gateway signs the user in through Keycloak, keeps their tokens server-side, and calls the API with a short-lived internal JWT. The API holds all business logic and stores everything in Postgres, except uploaded files.

4. Bounded contexts

The API is one process that hosts seven bounded contexts. Each is its own class library, so the compiler stops one context from using another's internals. They share one Postgres database through Marten.

A context that publishes integration events has a CommonGround.<Context>.Contracts project; its Events folder holds the event types other contexts may react to. Which contexts talk to which can be read from the project references to *.Contracts.

5. How a request flows

Example: a staff member records that a household finished housing counseling.

sequenceDiagram
  autonumber
  participant B as Browser

  B->>G: POST /api/... + cookies
  G->>G: CSRF check, session, mint JWT
  G->>A: same request + Bearer JWT
  A->>A: JWT, trust membership

  H->>M: load Household
  H->>H: decide: returns event
  H->>M: append, project, outbox
  M-->>W: publish events
  W->>W: other contexts' handlers
  A-->>G: 200 or problem
  G-->>B: response
  1. The browser sends the request with its cookies, plus the cg_csrf value as a header.
  2. The gateway checks the CSRF header, finds the session from cg_session, and mints an internal JWT.
  3. The gateway's endpoint calls the API through a typed client in CommonGround.API.Clients.
  4. The API validates the JWT and checks the user still belongs to the trust.
  5. The API endpoint sends the RecordHousingCounseling command with bus.InvokeForTenantAsync(trustId, …).
  6. Wolverine loads the Household aggregate for the handler ([WriteAggregate]).
  7. The handler calls household.RecordHousingCounseling(…), which returns an event or null.
  8. In one transaction: the event is appended, inline projections update, and outgoing messages are stored.
  9. Marten publishes the events to Wolverine.
  10. Other contexts' handlers run on durable local queues, each in its own transaction. The response doesn't wait for them.
  11. The API returns 200, or a problem response with an error code.
  12. The gateway passes the response to the browser.

The handler for that example is src/CommonGround.HomeBuyers/Application/Commands/RecordHousingCounseling.cs. It is a static method: Wolverine loads the aggregate, the handler calls one decision method, and Wolverine appends whatever event comes back. If the method returns null, nothing is written.

6. Domain model rules

  • Aggregates are deciders. A decision method checks the request against current state and returns the event(s) it decides on, without changing state. Marten rebuilds state by calling the aggregate's public static Create for the first event and a public Apply for each later one. An event without a public Apply is silently ignored when state is rebuilt.
  • Every domain type derives from a SharedKernel base class and starts from a dotnet new template in templates/ (ddd-aggregate, ddd-entity, ddd-vo, ddd-enum).
  • Bad input a user can send is a business rule violation, not an ArgumentException. The exception handler turns it into a problem response with an error code, and every error code has a message.
  • A rule used in two places is a missing concept. Extract it into a value object or domain service, as was done for Money and IncomeLimitTable.

7. Persistence

The API stores all state with Marten on Postgres. Setup is in src/CommonGround.SharedKernel/Extensions/MartenServiceCollectionExtensions.cs.

  • Event sourcing. Each aggregate is an event stream in the commonground_events schema, with string stream IDs. The event log is the record of what happened and when, which a CLT needs for audits and reports.
  • Read models are Marten projections that turn events into documents for queries. The projections in this code are registered Inline, so they update in the same transaction as the events. Each context registers its own in Infrastructure/Persistence.
  • Tenancy. Every document and every event is tagged with its trust (AllDocumentsAreMultiTenanted, TenancyStyle.Conjoined). Code opens a session for one trust and can't see another trust's rows.
  • Schema. Marten applies database changes at startup. The project has never been deployed, so there are no migrations yet; npm run db:reset is always safe in development.

The gateways store their sessions and ASP.NET Data Protection keys in their own Postgres schemas (management_gateway, homeowner_gateway) and read nothing else there.

8. Messaging between contexts

Wolverine is both the in-process mediator (endpoints call handlers through IMessageBus) and the message bus between contexts. Setup is in src/CommonGround.API/Program.cs.

  • Contexts don't call each other. When one context needs to react to another, the publisher puts an event type in its *.Contracts/Events folder, and the subscriber writes a handler for it. Example: PurchaseClosed from Homeownership.
  • A party's name changes at the boundary. Each context has its own language (see the glossary), so the subscriber translates. A household in Home Buyers becomes the buyer on a Homeownership purchase workflow when ApplicationSelected arrives (ApplicationSelectedHandler), and the buyer becomes the homeowner on the ground lease when the purchase closes. Stewardship knows only the homeowner.
  • Durable local queues. Messages are stored in the Postgres inbox/outbox in the same transaction as the events. They survive a restart, and scheduled messages (a prequalification expiring months later) are stored and polled for.
  • One handler per context per event (MultipleHandlerBehavior.Separated). Each runs on its own queue with its own transaction and retries, so one context's failure doesn't roll back another's.
  • Concurrency. Two handlers writing the same stream at once: the loser gets a version conflict and is retried after 50, 100 and 250 ms, reloading what it writes.
  • Handlers run at the time of their cause. EventClockMiddleware sets the clock to the event's time, so a reaction is dated when its cause happened even if it's delivered late, and seeded data gets reactions on the seeded date.
  • No event is dropped silently. A handler that can't act logs or fails.
  • Handler class names end in Handler or Consumer, or Wolverine doesn't find them.

Messaging:Transport can also send integration events to an external transport, for when a context is split into its own service: None (default), Postgres (one queue table, no extra container) or RabbitMq. Handlers inside the API receive the events with every setting.

9. Trusts, users and sign-in

  • The gateway is the only OIDC client. Keycloak tokens never reach the browser or the API. They are stored server-side in the gateway's sessions table, keyed by the cg_session cookie.
  • Cookies: cg_auth (ASP.NET cookie ticket), cg_session (HttpOnly session ID), cg_csrf (readable by JavaScript, sent back as a header for CSRF checks).
  • For each API call the gateway mints an internal JWT (HS256, 5-minute lifetime) with user_id, tenant_id (the trust) and session_id. The API takes identity from user_id and the tenant from tenant_id.
  • On first sign-in the gateway calls the API's EnsureUser with a service token, so users are created just in time.
  • TrustMembershipMiddleware in the API refuses a request whose user is no longer a member of the token's trust. Without it a removed member would keep access until their session expired (up to 7 days).
  • A new user gets into a trust in one of three ways: creates one in Onboarding, accepts an invitation, or tries a demo sandbox.

10. Dates and times

  • An instant (when something happened) is a UTC DateTimeOffset.
  • A calendar date (a lease start, a due date) is a DateOnly in C# and a CalendarDate in the web app.
  • "Today" is in the trust's time zone: ITrustClock in C#, trustToday() in the web app. A trust in Hawaii and one in Maine have different todays at the same instant.
  • Code reads the time through ITimeProvider, never DateTime.Now, so tests and seeders can set the clock.

11. Today: the work queue

The Today page lists everything that needs a staff member: an application awaiting a decision, a lease fee notice coming due, a document to review. No context owns this list. Each context derives WorkItems from its own read models in response to a query (GetHomeBuyersWorkItems, GetDocumentsWorkItems, GetRemindersWorkItems, and so on), and src/CommonGround.API/Today/TodayEndpoints.cs asks each one and merges the answers. A new kind of work item needs no change outside its own context, except the web app, which skips kinds it doesn't know.

12. Document files

Only the Documents context reads or writes files, through IDocumentBlobStore. Documents:Store picks the store: FileSystem (default; a mounted volume) or S3 (any S3-compatible bucket; MinIO in development). The S3 store redirects downloads to a presigned URL. With the file system store the API streams the file, and the gateway serves it with Content-Disposition, nosniff and a sandbox CSP so an uploaded HTML or SVG file can't run script on the app's origin.

13. The web app

  • React 19, Vite, React Router 7, TanStack Query 5, Tailwind CSS 4; tests in Vitest.
  • Code is organised by page under src/pages/<area>/, with shared components in src/components/ and data hooks in src/hooks/.
  • The API client in src/api/ is generated, not hand-written: npm run management:web:generate builds the gateway, exports its OpenAPI spec with NSwag, and runs OpenAPI Generator (typescript-fetch). Re-run it after changing a gateway endpoint or contract.
  • The gateway forwards API contracts to the browser, so a new required request field breaks the web forms and e2e tests until they send it.
  • Business defaults (what a field starts as) live in the client. On the wire, a null field and an absent field mean the same thing.

Each user-facing journey has a doc in docs/journeys/ describing the screens, entry points and outcomes.

14. Deployment

deploy/compose.yml runs five containers on one server: Caddy, Postgres, Keycloak, API and management gateway, plus a documents volume. Caddy gets TLS certificates and sends traffic to the gateway, and /auth-server to Keycloak. A small cloud server with 2 vCPU and 4 GB RAM is the target; Keycloak is the largest consumer at about 1.25 GB planned.

Backup is a nightly pg_dump plus a copy of the documents volume (or the S3 bucket). The server never seeds data. The same setup serves an operator who hosts many CLTs and a CLT that hosts its own copy. How to set it up: docs/hosting.md.

16. Decisions and their reasons

DecisionReason
One API process with seven bounded contexts, not microservicesOne small server is cheap for a nonprofit to run. Separate projects and integration events keep the contexts apart, so one can be split out later by changing Messaging:Transport.
Event sourcing with MartenCLT work is a long history (a lease lasts 99 years, a home resells several times). Audits and reports need what happened and when, not only current state. Marten gives that on plain Postgres.
Postgres for everything except filesOne database to run and back up. Redis and RabbitMQ were removed from the default setup; config can bring them back when load requires it.
A BFF gateway in front of the APITokens stay off the browser. The app, /api and /auth share one origin, so cookies stay first-party and no CORS is needed.
Keycloak for sign-inIt gives sign-up, password reset, lockout and two-factor sign-in without the project writing security code. Replacing it with ASP.NET Core Identity is planned if an operator needs a 2 GB server or Keycloak upgrades break.
Conjoined tenancy (one database, rows tagged by trust)A shared instance can host many small CLTs at low cost. Marten enforces the separation per session.
