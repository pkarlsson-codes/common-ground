Glossary Decisions

Why each term in the glossary was chosen over its rivals. The glossary says what to write; this page says why, so a later change can tell whether the reason still holds.

Counts: the Grounded Solutions CLT Technical Manual (2011), docs/clt-manuals/markdown/, case-insensitive, singular plus plural, counted 2026-11-14.

1. How terms are chosen

  • A language belongs to one bounded context. Inside a context, one concept has one word. Across contexts the same party may have different words (household, buyer, homeowner), and the same word may mean different things (member, schedule). Each context's "Do not use" column carries the clash; the architecture page's messaging section shows where a party's name changes.
  • The manual's word wins when the manual uses it far more often than any rival and it fits the code's model. Where the manual splits between words, the model decides.
  • The word staff say out loud wins over the legal word. The legal word stays in lease text.
  • An existing code name wins when the manual has no clear word and the code name is accurate.
  • A word that already means something else in the app is out, even if the manual uses it.

3. Identity

TermWhy
Trust member / staffThe code has no type for it: the membership is on User, and the commands say "trust member" (ListTrustMembers, RemoveTrustMember). Staff say "staff". Journeys say "user" about 500 times, mostly UI actions ("user clicks"), which stay. "Staff" is for the person deciding, so only sentences about decisions change. "Member" alone is out because Home Buyers has household members.

5. Home Buyers

TermWhy
HouseholdBy count, buyer (335) plus homebuyer (221) beat household (241). The model decides instead: Household exists before any application and after any purchase, so "buyer" would be wrong for most of its life.
ApplicantThe manual uses it only 20 times. Kept because the code uses Applicant and SelectApplicant, and it is accurate when the sentence is about the application.
ReadinessThe manual has no clear word (readiness 2, buyer preparation 0), so the code name wins: ReadinessItem, IsReadinessComplete, HouseholdReadinessIncomplete, the household phase Ready, and the "Readiness" column. An earlier version chose "buyer preparation" after the UI heading; it was dropped because "buyer" is Homeownership's word, and Home Buyers says household.
ApplicationDocs and UI already say it. The code name HomeownerApplication misleads, because the household is not yet a homeowner.
Waiting listWaiting list 11, wait list 0. Thin evidence, but unanimous.
Home selectionMatches the HomeSelection aggregate. "Assignment" or "allocation" would add a second name for it.
Income limitMatches the code and the income limit schedule. "AMI cap" names one way of setting a limit, not the limit.
Income limit scheduleMatches IncomeLimitSchedule. "Schedule" alone is out because Homeownership has notice schedules.

Purchase workflowMatches PurchaseWorkflow. UI and journeys shorten it to "purchase" because staff don't say "workflow". "Sale" is out because a resale is also a sale.

Ground lease templateMatches GroundLeaseTemplate. The manual says "model lease" 147 times, but it means its own published lease; using it for the trust's terms would point readers at that document.
Lease feeLease fee 304, ground lease fee 21. "Rent" implies a tenant who doesn't own the home.

9. Verbs

The verbs come from the code's command and event names. In the glossary each verb sits under its noun, because a verb is a command on one aggregate: "withdraw" on an application and "withdraw" on a purchase have different preconditions, effects and events (ApplicationWithdrawn, PurchaseWithdrawn), so they are two verbs. An earlier version grouped same-spelled verbs in the Shared Kernel; that treated spelling as meaning and crossed context lines. What the same-spelled verbs share is a naming convention, kept in docs/ai/ubiquitous-language.md. The reasons for those conventions follow.

VerbWhy
withdraw / cancel / failA purchase can be both withdrawn and failed (WithdrawPurchase, FailPurchase), so the two must mean different things. The code comments give the split: withdraw is "the buyer has withdrawn"; fail needs a failure reason. Across the code, withdraw is always the party that started something (application, purchase, intent to sell, mortgage request), and cancel is always the trust's own process (home selection, invitation, property inspection). The one exception, WithdrawForRedevelopment on a land parcel, is listed under Not yet matching.
approve / denyUsed for both requests the trust decides (application, mortgage request), in code and UI. "Reject" is out because the occupancy verification UI already uses it for what the code calls fail.
recordKept for facts that happen outside the app, because most Record* commands are that (RecordAppraisalCompleted, RecordTitleCleared, RecordPurchaseClosed). Limiting it to those makes the ones that hide a decision stand out.
correct / edit / voidThe code already uses three different verbs for three different changes: CorrectLeaseFeeTracking ("such as after an import with the wrong date"), EditPermittedMortgage ("such as when servicing moves to another company"), VoidLeaseFeePayment ("a payment recorded by mistake"). Edit wins over update because the one domain object that changes for real-world reasons in Homeownership uses it; Home Buyers' update is listed under Not yet matching.
cure / resolveCure is the manual's word (99 uses, against 16 for resolve) for fixing a default or violation, and the code uses it (CureViolation, ActivateCurePeriod). Resolve is kept for the foreclosure prevention case because it ends with an outcome (ForeclosurePreventionOutcome), which may not be a cure.
pass overMatches PassOver. The code comment draws the line: an application that couldn't have been selected isn't passed over, so "skipped" would be wrong.
exercise / decline"Exercise" is the legal verb for an option and matches ExerciseOption. "Decline" matches the journey; the code has no decline command yet.

10. Weakest choices

  • Land parcel and applicant rest on the code, not the manual.
  • Waiting list rests on 11 uses.
  • Household over buyer goes against the raw counts, because the model says so.
