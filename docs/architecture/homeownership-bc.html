Key Decisions

  • Per-home AmiEligibilityTier on GroundLease: Each ground lease carries the maximum AMI tier allowed for that unit — determined at creation time by the unit's funding source (HOME funds, CDBG, CLT own equity). This resolves the open question from the Applicant Pipeline BC: the constraint lives here, and offer-matching logic must verify that a buyer's qualified AMI tier does not exceed the unit's AmiEligibilityTier before calling ExtendOffer().
  • OriginalPurchasePrice and OriginalAppraisalValue are stored separately in ResalePolicyTerms: The subsidized price the homeowner paid (OriginalPurchasePrice) and the unencumbered market appraisal at time of sale (OriginalAppraisalValue) are two distinct values. The appraisal-based resale formula uses the appraisal delta; conflating these two numbers would produce an incorrect resale price. The current implementation does not store either — this is a known gap that must be filled before any resale calculation can run.
  • PurchaseWorkflow has five parallel tracks, not sequential stages: Eligibility verification, financing commitment, inspection, title clearance, and lease execution can all proceed concurrently. The saga advances from InProgress to ClosingScheduled only when all five are satisfied. This is accurate to how CLT transactions work — buyer financing and property inspection typically run in parallel. StallWorkflow() handles cases where one track is blocked without terminating the rest.
  • PurchaseWorkflowTrigger distinguishes buyer role: The same saga structure handles three scenarios — a waitlisted buyer accepting an offer (WaitlistOffer), CLT waiving ROFR and an external buyer proceeding (ROFRExpiredExternalBuyer), and CLT exercising ROFR to purchase the home itself (ROFRExercisedCLTBuyer). The Trigger field records which scenario this workflow represents; Homeownership logic uses it to determine whether to set GroundLeaseStatus to CLTOwned vs. Active on PurchaseClosed.
  • ROFRExercised path uses two sequential PurchaseWorkflows with CLTOwned interim: When the CLT exercises first refusal, it runs one PurchaseWorkflow (CLT as buyer) that closes with GroundLeaseStatus = CLTOwned. The CLT then immediately initiates a second PurchaseWorkflow (WaitlistOffer trigger) for a waitlisted buyer; PurchaseClosed on that workflow transitions GroundLease back to Active with the new homeowner. Two workflows, not a special case.
  • StewardshipCheckIn does not belong on GroundLease [implementation debt]: The current implementation has RecordStewardshipCheckIn() on GroundLease, emitting StewardshipCheckInRecorded. This is a placeholder. Annual visits are relationship and compliance work — the outputs (violations, distress signals, follow-up cases) all live in the Stewardship BC, not Homeownership. GroundLease has no business recording them. The method and event should move to StewardshipCase in the Stewardship BC; if a visit surfaces a lease-level consequence (e.g., an unauthorized improvement must be approved or removed), Stewardship emits a cross-BC event that Homeownership handles. This page's diagrams omit the misplaced method intentionally.
  • GroundLeaseStatus needs to expand beyond Active/Inactive: The current implementation has only Active and Inactive. The full ROFR workflow requires PendingResale (NOIS filed, clock running), CLTOwned (interim after ROFR exercise), and Terminated (lease ended). These states should be added when NoticeOfIntentToSell is implemented.
  • ImprovementRequest is a per-item aggregate, not a scalar: Each improvement (deck, HVAC, solar panels) has its own approval, approved cost, depreciation schedule, and actual cost at completion. The depreciated remaining value of all completed improvements is summed at resale time to compute the improvement credit. A single decimal field on GroundLease would lose all of this history.
  • MortgageConsent is a discrete record per refinancing event: When a homeowner refinances, the CLT reviews the new loan terms against the ground lease's mortgage restrictions (LTV cap, lender acceptance of lease terms) and issues written consent. Each consent is its own aggregate — not a flag on GroundLease — because CLTs audit these records for compliance with recognition agreements.
  • LenderRecognitionAgreement is executed once per lender per lease: This tri-party instrument (CLT + homeowner + lender) grants the CLT a 60-day cure period on mortgage default before foreclosure can proceed. Once executed, it covers the full life of that financing relationship with that lender. It lives in Homeownership (not Lease Finance) because it governs lease terms, not payment terms.
  • EstoppelCertificate has a 10-business-day response obligation: Lenders demand this before any financing closes — it certifies the lease is in good standing, no known defaults, and lease fees are current. The Overdue state exists because the CLT has a legal and reputational obligation to respond promptly; tracking overdue certificates allows staff to prioritize.
  • Fixed-percentage formula must use fractional years: Rounding to integer ownership years introduces meaningful price distortion on mid-year resales. The formula should compute days / 365.25 for the appreciation exponent, not integer year count.
  • Improvements do not affect the index-based resale formula: The index adjustment (AMI or CPI) already accounts for value growth. Only the appraisal-based and itemized formulas use improvement costs in the resale price calculation. This distinction must be enforced in the resale calculation logic, not left to caller conventions.

Open Questions

  • AmiEligibilityTier granularity: The current AmiQualificationTier enum has three values: VeryLow (≤50%), Low (51–80%), Moderate (81–120%). Some HOME-funded units require ≤60% AMI — a threshold our enum can't represent precisely. Options: add a SixtyPercent tier to the shared enum, store the raw AMI percentage cap as a decimal on GroundLease instead of an enum, or accept that 60% units are categorised as VeryLow (conservative). Which approach matches operational reality for this CLT?
  • StewardshipCheckIn on GroundLease: The current implementation has RecordStewardshipCheckIn() on GroundLease, emitting StewardshipCheckInRecorded. But Stewardship is modelled as a separate bounded context (StewardshipCase aggregate) with its own team and language. Should annual visit check-ins live on GroundLease (Homeownership) or on a StewardshipCase (Stewardship BC)? Keeping it on GroundLease couples two BCs in one aggregate. Moving it to Stewardship BC means GroundLease emits an event that StewardshipCase handles. This is a real design question — what's your preference?
  • CLTOwned phase modelling: When CLT exercises ROFR, does the existing GroundLease transfer to CLT (GroundLeaseStatus = CLTOwned, CurrentHomeowner = CLT entity) or does it terminate and a new GroundLease get created with CLT as homeowner? The first approach is simpler but means GroundLease holds CLT as a homeowner, which is semantically odd. The second is cleaner but loses the continuity of the lease record.
  • ResalePolicyTerms — IndexType as string vs enum: The current implementation stores IndexType as a plain string (e.g., "AMI", "CPI"). This works but loses compile-time safety and makes the index calculation logic branch on string comparison. Should this become an AmiCpiIndexType enum?
  • Itemized formula not yet modelled: FormulaKind includes Itemized as a value but ResalePolicyTerms has no factory method or fields for it. The itemized formula credits improvement costs with an explicit depreciation schedule — essentially the sum of ImprovementRequest approved/completed records. Does this formula type pull from ImprovementRequest at resale time, or does it store its own improvement schedule on ResalePolicyTerms?
  • RenovationProject aggregate in Property Registry: Building currently has status transitions (RenovationStarted / RenovationCompleted). For major CLT rehabs, there are contractor scopes, permits, and inspections tracked over months. Does this warrant a dedicated RenovationProject aggregate in Property Registry, or are Building status transitions sufficient?
