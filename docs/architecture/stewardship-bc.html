Key Decisions

  • ViolationRecord is not a top-level aggregate. CLT software (HomeKeeper, Public House) models violations as child records of a persistent stewardship file, not standalone cases. Violations do not exist independently — they arise within the context of an active homeowner relationship and are worked by the same coordinator managing that file. Elevating ViolationRecord to a top-level aggregate in the preliminary domain map was a modeling error; corrected here.
  • Two OccupancyVerification types, one entity. Annual surveys submitted by the homeowner and occupancy visits performed by staff both produce an OccupancyVerification record. The source differs (homeowner self-report vs. in-person inspection) and the fields differ (SubletDisclosed / MajorChanges vs. OccupancyConfirmed / ConditionNotes), but the lifecycle is identical. Modeling them as the same entity keeps the aggregate interface simple; a future homeowner portal uses the same SubmitOccupancyVerification path, just submitted via a different surface.
  • CurrentHomeowner is not denormalized into aggregates. Both StewardshipCase and ForeclosurePreventionCase hold GroundLeaseId only. Homeowner contact information is a read-model concern: the coordinator's view resolves it at query time via GroundLeaseId. Denormalizing creates a stale-data sync problem — if HomeownerChanged fires, every aggregate holding a Homeowner value object must be updated with no write-side benefit.
  • ServicerDelinquency is manual-entry for now. Lender servicer feeds (Fannie Mae reporting, servicer portals) require integration work that is out of scope for the initial build. Staff manually enters the delinquency via RecordServicerDelinquency(). The domain event ServicerDelinquencyRecorded is clean enough that an automated servicer feed can drive the same command later with no model changes.
  • ForeclosurePreventionCase uses typed child entities (Approach B). CurePeriodActivation is a legal action: it references a specific LenderRecognitionAgreement (LraId), sets a cure deadline, and tracks the cured amount and outcome. This record is referenced in compliance reporting and must stand as a first-class audit entry. ForbearanceRequest and CounselingReferral also warrant individual outcome tracking for CLT compliance reporting — not just aggregate counts.

Open Questions

  • OccupancyVerification auto-initiation cadence. Who or what creates the annual OccupancyVerification record? Options: a scheduled Wolverine saga that fires annually per active StewardshipCase, a batch job on a Hangfire-style scheduler, or manual staff action. The domain model is neutral on this — InitiateOccupancyVerification() is a command that any caller can issue — but the infrastructure and scheduling approach must be decided before building the feature. A Wolverine saga keyed off anniversary of OpenedDate is the most event-native approach.
  • ForeclosurePreventionCase deduplication. If both a LeaseFeeArrearsEscalated integration event and a manual ServicerDelinquency entry arrive for the same GroundLeaseId within a short window, should the system open one case or two? Likely one — the coordinator works a single file regardless of how the distress was first detected — but the merge/deduplication rule must be defined: check for an open ForeclosurePreventionCase on the same GroundLeaseId before opening a second, and if one exists, record the additional trigger on it rather than creating a duplicate.
