Key Decisions

  • HousingCounselingCompleted gates the Application: CLTs universally require HUD-certified housing counseling before a formal application opens. This is a real gating precondition — not a checkbox — and belongs as an explicit state transition on InterestRegistration. Staff records counselor name, completion date, and optional certification number.
  • InterestRegistration is a separate aggregate from Application: The pre-application funnel (interest form, information session, counseling) has its own lifecycle and can be withdrawn without ever producing an Application. Keeping them separate preserves that independent history and avoids a bloated Application aggregate.
  • DocumentsSubmitted does not change ApplicationStatus: Applications stay Open until a staff decision (Approved/Rejected). DocumentsSubmitted is an audit event — it records when documents arrived and allows tracking of slow-moving applications without creating intermediate states that require handling.
  • AMI tier recorded at approval, not at intake: Income is verified by staff during application review (pay stubs, tax returns). The tier determines which price-restricted units the applicant qualifies for and follows the WaitlistEntry to the PurchaseWorkflow. AmiQualificationTier values: VeryLow (≤50% AMI), Low (51–80% AMI), Moderate (81–120% AMI) — most CLT homeownership programs target Low tier. The tier name alone is not sufficient for audit: ApplicationApproved also captures verifiedHouseholdIncome (the applicant's actual verified income) and amiReferenceFigure (the HUD-published AMI for this region/year at time of approval). HUD publishes updated figures annually; recording the reference figure at approval time means the qualification decision is auditable even after HUD updates the number.
  • WaitlistEntry holds denormalized applicant contact: The integration event to Homeownership BC needs buyer contact info. Denormalizing it onto WaitlistEntry avoids a cross-BC query at offer-acceptance time and keeps the event payload self-contained.
  • OfferDeclined cycles back to Active, not to end of queue: Declining an offer does not terminate the WaitlistEntry. The entry stays active and can receive future offers. OffersDeclinedCount is tracked so staff can see repeated declinations (often a signal that the applicant's circumstances have changed).
  • Withdrawn vs Deactivated on WaitlistEntry: Withdrawn is applicant-initiated (they've decided not to proceed). Deactivated is staff-initiated for administrative reasons (lost contact, moved out of area, income no longer qualifies, deceased). Both are terminal states but have different operational meaning for reporting.
  • WaitlistPriorityTier is a four-value enum, not a score: CLTs implement preference criteria defined in their bylaws (local resident, existing land renter, veteran). A flat tier enum is sufficient for initial implementation — multi-criteria weighted scoring can be added later without breaking the aggregate's event model.
  • Integration event named PurchaseWorkflowRequested, not OfferAccepted: The integration event crosses a BC boundary and carries buyer + property data that Homeownership BC needs. Naming it from the perspective of what Homeownership needs to do makes the contract explicit. OfferAccepted remains a domain event on WaitlistEntry; PurchaseWorkflowRequested is the outbound integration event derived from it.
  • MemberId is an optional string reference, not a foreign key: The identity correlation between applicants and CLT members is loose. Membership BC is not yet implemented. InterestRegistration holds an optional MemberId (string) that can be populated if the applicant is also a member — no hard dependency on Membership BC.

Open Questions

  • Waitlist position management: This model tracks each WaitlistEntry in isolation. The actual FIFO ordering (position 1, 2, 3… within a priority tier) is a query concern, not an aggregate concern. Where does the ordering live — a projection, a dedicated WaitlistQueue read model, or a managed list aggregate? Who sets priority tier — is it auto-derived from the Application's verified data or manually assigned by staff?
  • Multiple active InterestRegistrations per person: Should a person be allowed to submit a new InterestRegistration if they already have an active one? Could happen if their previous Application was rejected (Rejected status is terminal) and they want to re-apply after improving their situation. Model currently has no guard against this — is that correct?
  • Application after rejection — re-application pathway: If an Application is Rejected, the applicant must re-apply. Does that start a new InterestRegistration (going through counseling again) or a new Application directly (skipping counseling if recently certified)? HUD counseling certificates typically expire after 12 months.
  • Offer expiry enforcement: OfferDetails carries an OfferExpiryDate but the model has no mechanism to enforce it. Who drives expiry — a scheduled job that deactivates OfferPending entries past their expiry date, or staff who manually record a declined/withdrawn decision? Impacts whether this BC needs an async scheduler.
  • Multiple active WaitlistEntries per applicant: Can an approved applicant have more than one WaitlistEntry? Unlikely in normal operations, but could occur if the first entry is deactivated (staff error) and a new one is created. Should the Application guard against creating a second WaitlistEntry while one is still active?
  • AmiTier at offer time vs at approval time: AMI qualification is recorded at application approval. By the time an offer is extended (potentially months or years later), the applicant's income may have changed. Do CLTs re-verify income at offer time? If so, should AmiTier be updateable on WaitlistEntry, or does re-verification produce a new Application?
  • Per-home AMI eligibility constraints (Homeownership BC concern): Some units carry funding-source restrictions — a HOME-funded unit may require ≤60% AMI regardless of the program's default ≤80% ceiling. This BC records the applicant's qualified tier, but there is currently no model for which tiers a specific home accepts. That constraint likely belongs on the GroundLease or a property attribute in Homeownership BC, and the offer-matching logic must enforce it before ExtendOffer() is called.
